**Title:** On Linux, a "no" to browser cookies does not stop the extras-host CDP and agentcookie lookups on later runs

**Body:**

The first-run wizard asks before any cookie read, and SKILL.md says "a skip or no answer is never consent" (line 542) and "Does not access browser cookies unless explicitly configured or consented" (line 2415). On Linux that holds for the setup run itself, but not for the research runs after it.

What happens at `5103ba4`:

1. The user answers no. The skill runs `FROM_BROWSER=off ... last30days.py setup` (SKILL.md line 664). `FROM_BROWSER=off` lives only in that process's environment. Because no browser yielded cookies, `from_browser` is `None` (`last30days.py` line 3336), so `write_setup_config` appends only `SETUP_COMPLETE=true`, and setup prints "Configuration saved. Future runs will auto-detect your browsers." "Skip for now" writes the same single line.
2. The next research run builds its config with `browser_cookies="read"` (`last30days.py` line 2894), which calls `_discover_and_apply_x_credentials`.
3. `x_extras_enabled` returns `True` for every Linux host (`env.py` line 913), so the agentcookie sidecar runs if it is on `PATH`, and `chrome_cdp.read_x_cookies` probes `127.0.0.1:18800`, then `127.0.0.1:9222 + $DISPLAY`. Both run before the mainline `FROM_BROWSER` gate (`env.py` lines 980 to 1000). If a Chrome answers, the engine sends `Network.getAllCookies` (`chrome_cdp.py` line 285), which returns every cookie that browser profile holds, and keeps the x.com pair.

How we checked it, with no real browser and no real cookies: a scratch `HOME`, `FROM_BROWSER=off python3 last30days.py setup` (the `.env` it wrote held only `SETUP_COMPLETE=true`), then the same `env.get_config(policy=_config_policy_for_args(...))` call `main()` makes for a plain topic. A small local server answering as Chrome on port 18800 logged `GET /json/version`, `GET /json`, the websocket upgrade, `Network.enable` and `Network.getAllCookies`; the config came back with `AUTH_TOKEN` from source `chrome cdp`, and `get_x_source_with_method` returned `('bird', 'chrome cdp')`. The same happened on 9222 with `DISPLAY=:0`. With a stub `agentcookie` on `PATH`, it was called as `agentcookie cookies --domain .x.com --json` and its pair was used. With `FROM_BROWSER=off` and `AGENTCOOKIE=off` both in the `.env`, neither lookup ran.

CONFIGURATION.md documents the extras-host lookups (lines 195 to 204), but line 91 says a "no" "skips all cookie reads", so a user who declined has no reason to expect them. When a pair is found, the engine uses it to search X as that user through the vendored scraper.

Possible fixes, smallest first:

- When the user says no or skips, persist the answer: append `FROM_BROWSER=off` and `AGENTCOOKIE=off` (or a single `BROWSER_CONSENT=false`) next to `SETUP_COMPLETE=true`, and have the SKILL.md "no" and "Skip for now" branches write it.
- Gate the extras on recorded consent: run agentcookie and CDP only when `BROWSER_CONSENT=true`, `FROM_BROWSER` names a browser, `BROWSER_CDP_URL` is set, or `AGENTCOOKIE=on`. A user who followed the box-chrome login recipe sets `BROWSER_CDP_URL` anyway.
- Ask Chrome only for what the engine needs: `Network.getCookies` with `urls: ["https://x.com", "https://twitter.com"]` instead of `Network.getAllCookies`.
