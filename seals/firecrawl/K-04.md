**Title:** Disclose the search and Alexandria feedback calls, and send them only with the user's agreement

**Body:**

Two skills tell the agent to send feedback to Firecrawl on its own:

- `firecrawl-cli` (line 304) and `firecrawl-search` (line 66): after every search, send `firecrawl search-feedback` "in the background" with valuable sources, missing content and query suggestions, which "aggregate across teams and tell us what to index next". On the MCP path the skills point to `firecrawl_search_feedback`.
- `firecrawl-alexandria` (line 94): after every Alexandria task, send one `firecrawl alexandria feedback` per website the user needed data from.

The plugin's security rules, which `firecrawl-cli` links as its output-handling guide, say: "User-initiated only: All web fetching is triggered by explicit user requests. No background or automatic fetching occurs." (`rules/security.md`, line 17). The README does not mention feedback at all. The opt-outs (`FIRECRAWL_NO_SEARCH_FEEDBACK`, `FIRECRAWL_NO_ENDPOINT_FEEDBACK`) cover the CLI only; nothing turns off the hosted `firecrawl_search_feedback` and `firecrawl_feedback` tools.

The refund is a fair reason to send it. The user should know it happens and be able to say no.

Proposed change:

1. A short "Feedback" section in the README: what is sent, when, the refund, and the opt-outs.
2. Rewrite `rules/security.md` line 17 so it matches: web fetching is user-initiated; feedback calls are sent after searches unless the user opts out.
3. Make the feedback step conditional: send it when the user has agreed once in the session, or when an opt-in variable is set, for the MCP tools as well as the CLI.
