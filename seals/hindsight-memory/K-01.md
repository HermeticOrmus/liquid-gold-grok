**Title:** In Grok Build, auto-recall context is discarded and the transcript is in a different format

**Body:**

`scripts/recall.py` returns recalled memories as `hookSpecificOutput.additionalContext` from the `UserPromptSubmit` hook (line 216 at `31a1260`). That works in Claude Code.

Grok Build's hooks guide says of `UserPromptSubmit`: an allowing hook's stdout and `additionalContext` are discarded rather than added as context (`docs/user-guide/10-hooks.md` line 481 in xai-org/grok-build). The prompt gate in the Grok source returns only the allow or block decision (`hook_dispatch.rs` line 444). The same text ships with grok 1.0.44.

So in Grok, auto-recall cannot inject anything. I have not watched this in a live session; the evidence is Grok's own documentation and source.

Possible directions:
- Deliver the recall block through an event whose context Grok keeps. Grok delivers `additionalContext` from `PreToolUse` and `PostToolUse` hooks next to the tool result, so the first tool call of a turn could carry it.
- Or document that in Grok, recall happens through the `agent_knowledge_recall` MCP tool (see the separate issue about the MCP server not starting).
- Or ask xAI to keep `UserPromptSubmit` context, as Claude Code does.

A second point in the same area: `scripts/retain.py` (line 38) reads `transcript_path` as Claude Code JSONL, looking for `{type: "user" | "assistant", message: {role, content}}` or flat `{role, content}` lines. In Grok, `transcript_path` is the session's own `updates.jsonl` (`xai-grok-shell/src/session/compaction.rs` line 518), and Grok's status-line guide says of that file: "The file is Grok's own update stream, so a script that parses another tool's transcript format will not read it" (`docs/user-guide/25-status-line.md` line 90). If that holds for the hook payload too, retain finds no messages and stores nothing. I have not read a Grok `updates.jsonl` to confirm the shape.
