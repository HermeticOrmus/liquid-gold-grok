**Title:** Grok Build: deliver session-start memory through the first PostToolUse, since Grok drops SessionStart context

**Body:**

`contextHandler` returns the memory timeline as `hookSpecificOutput.additionalContext` from SessionStart (`src/cli/handlers/context.ts` line 232), and semantic injection returns it from UserPromptSubmit (`session-init.ts` line 303). Grok Build documents that it ignores SessionStart stdout (`docs/user-guide/10-hooks.md` line 505 in xai-org/grok-build) and discards an allowing UserPromptSubmit hook's `additionalContext` (line 481). #4282 notes the same and calls it a host limit.

There is a channel Grok does keep. For PostToolUse, the same guide says a hook's `additionalContext` "arrives after the tool result, wrapped in your harness's reminder tag", so the model reads it in the same turn. claude-mem already runs a PostToolUse hook on every tool (`observation`), and Grok runs it in the foreground because it ignores the `async` key (`xai-grok-hooks/src/config.rs` line 101 reads only `type`, `command`, `url`, `timeout` and `env`).

A possible shape:

- In the SessionStart context step, when the host is Grok Build, keep the rendered context for that `session_id` instead of relying on stdout. Grok sets `GROK_PLUGIN_ROOT` and `GROK_PLUGIN_DATA` for plugin hooks (`docs/user-guide/09-plugins.md` line 431), and its payload carries camelCase keys such as `hookEventName: "session_start"` and `workspaceRoot`, either of which can identify it.
- In the first PostToolUse of that session, return the stored context as `hookSpecificOutput.additionalContext` and mark it delivered. Grok clips that text at 10,000 characters, so the compact timeline fits better than the full one.
- Optionally ask xAI to keep SessionStart context, as Claude Code does.

We confirmed with a sandbox run at `e290f3d` that the context step prints a valid `additionalContext` block under Grok's payload; we did not watch a live Grok session, so the claim that it never reaches the model rests on Grok's documentation.
