**Title:** Accept Grok's native tool names as well as the Cursor-style ones

**Body:**

Several hook paths compare the tool name against Cursor-style names only:

- `internal/cmd/post_tool_read.go` line 21 returns unless the tool is `read`;
- `internal/cmd/post_tool_todo.go` line 20 returns unless it is `todowrite`;
- `internal/hashline/validate.go` line 18 checks `strreplace`, `str_replace`, `edit`, `multiedit`, `multi_edit`;
- `internal/lsp/posttool.go` line 15 checks `apply_patch`, `write`, `strreplace`, `str_replace`, `edit`, `multiedit`, `multi_edit`, `editnotebook`.

Grok's hooks guide documents its own names as `read_file` for Read and `search_replace` for Edit, Write and MultiEdit (`docs/user-guide/10-hooks.md` line 172), and its alias table maps `TodoWrite` to `todo_write` (`xai-grok-tools/src/types/claude_alias.rs` line 47 onward). The hook `matcher` fields fire on those names through the aliases, but the Go code then sees `read_file` or `search_replace` and does nothing.

Dry run of the `omg-hook` binary with Grok's event shape: `post-tool-read` on `read_file` wrote no hash cache and marked no skill, and a `pre-tool-use` edit with a stale `LINE#ID` in `old_string` was denied as `StrReplace` but allowed as `search_replace`.

If Grok Composer sessions use the Cursor-style names, the current code works there; accepting both sets would make it work in every Grok session. Suggested change: normalize the tool name once in `hookenv` (for example map `read_file` to `read`, `search_replace` to `strreplace`, `todo_write` to `todowrite`) before these checks.
