**Title:** Grok drops SessionStart output and UserPromptSubmit context; the skill gate then unlocks on content the model never saw

**Body:**

Grok's hooks guide (xai-org/grok-build, `docs/user-guide/10-hooks.md`) says two things that affect oh-my-grok, and the same text ships with grok 1.0.44:

- line 505: for `SessionStart`, stdout is ignored;
- line 481: for an allowing `UserPromptSubmit` hook, stdout and `additionalContext` are discarded rather than added as context.

`internal/cmd/session_start.go` (line 37) emits the skill-gate banner as `SessionStart` context, and `internal/cmd/user_prompt.go` (line 52) emits the merged per-prompt context: the first-prompt `using-superpowers` bootstrap, IntentGate banners and skill-gate reminders. Running the `omg-hook` binary outside a session with Grok's event shape, those came to 2,802 and 16,865 bytes. Per the guide, none of it reaches the model.

There is a knock-on effect on the gate. `internal/usingpowers/first.go` (line 93) calls `MarkSkillLoaded(sessionID, "using-superpowers")` when it builds the first-prompt context. After the first `user-prompt` run, `skills.loaded` holds `using-superpowers` and `pre-tool-use` allows edits, although in Grok the model never received that skill.

Suggested direction:
- Only mark a skill loaded from `post-tool-read`, when the agent actually reads its `SKILL.md`.
- Move model-facing guidance to channels Grok delivers: `PreToolUse` deny reasons and `additionalContext`, `PostToolUse` `additionalContext`, Stop feedback, or rules files the harness loads.

I have not watched this in a live Grok session; the evidence is Grok's documentation and a dry run of the hook binary.
