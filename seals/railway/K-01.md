**Title:** use-railway: trigger on Railway requests only, and ask before deploying on a sign-up request

**Body:**

The `use-railway` description (SKILL.md lines 3 to 19) tells the agent to use the skill "whenever the user mentions Railway, feature flags, flag rollout, targeting rules, signing up, creating an account, registering, logging in, deployments, services, environments, buckets, object storage, tracing, ... MCP, or infrastructure operations, even if they don't say \"Railway\" explicitly."

Most of those words come up in projects that have nothing to do with Railway: adding a login page, setting up feature flags with another provider, building an MCP server, tracing a service on another host. With this description the agent reaches for Railway first in all of them.

The sign-up route goes further. Line 91: "If the current directory has a deployable app ... run `railway up`" and "Use it even when the user only said \"sign me up\"". Line 187 adds that with an agent harness detected, `railway up` "skips the confirm prompt" and "the agent invocation is treated as consent". So a user who asks for an account gets their working directory uploaded and deployed, which is more than they asked for and is hard to take back if the directory holds code they did not mean to send anywhere. The deploy-intent route (line 86) already has the agent announce the deploy first; the sign-up route does not.

Proposed change:

1. Keep the trigger to Railway: drop "even if they don't say \"Railway\" explicitly" and the generic terms (signing up, logging in, feature flags, deployments, MCP, tracing), or qualify them with "on Railway". This also brings the description under the 1,024-character limit raised in #96.
2. On a sign-up request, run `railway login`, then offer `railway up` as a next step and wait for a yes before deploying.

The rest of the skill's safety habits (user-only database commands, confirmed intent for destructive actions, no deploy reported without SUCCESS) are good and need no change.
