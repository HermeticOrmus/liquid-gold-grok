**Title:** best-practices skill: document only the read-only Cloud MCP this plugin registers

**Body:**

The plugin README says the plugin connects only to `https://mcp.clickhouse.cloud/mcp`, stores no secrets, and that every MCP tool is read-only (`README.md` line 31). `.mcp.json` registers that one HTTP server. With grok 1.0.46, `grok mcp doctor clickhouse` starts it and the handshake stops on the server's OAuth challenge.

`skills/clickhouse-best-practices` does not set `disable-model-invocation`, so the model can follow it on its own. `rules/agent-connect-mcp.md` then tells the agent to:

- run `claude mcp add` (lines 27 and 42), which is Claude Code's command; this plugin already registers the server for Grok
- run `pip install mcp-clickhouse` with no version (line 50), so the code that runs is whatever PyPI serves (0.7.0 on 2026-10-04)
- pass the database password on the `clickhouse client` command line (line 75, `--password 'your-password'`) and in an `X-ClickHouse-Key` header (line 88)
- turn writes on with `export CLICKHOUSE_ALLOW_WRITE_ACCESS=true` (line 60)

`AGENTS.md` repeats those lines (1713, 1749, 1756). The remote MCP page says the hosted server's 13 tools are read-only. The write switch belongs to the self-hosted server, which this plugin does not start.

Proposed change: in `rules/agent-connect-mcp.md`, and in the generated `AGENTS.md`, describe the server `.mcp.json` already registers. Point sign-in at Grok's `/mcps` OAuth flow. Drop `claude mcp add`, the unpinned `pip install`, the password-on-the-command-line examples, and the write switch from this plugin. A self-hosted server can stay as a link to ClickHouse's own MCP server docs, with one sentence that it is a different server and that this plugin does not start it.
